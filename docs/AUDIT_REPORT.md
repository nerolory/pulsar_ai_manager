## Главный вывод (30 секунд)

Проект **рабочий как основа**, но **не готов отдавать пользователям без доработки**.

- **Сохранение чатов, интерфейс, сборка, Docker-образы** — в порядке.
- **Часть кнопок и API не стыкуется** — пользователь нажимает, ничего не происходит.
- **5 из 12 провайдеров в списке сейчас не подключаются** — нет библиотек или нет кода.
- **Локальные модели** — заявлены, но загрузка и запуск **не реализованы до конца**.
- **На Windows без Docker** приложение может **не найти папку для данных** — это первый блокер.

Объём: **полная доводка всех заявленных функций**, не «минимальный фикс». Ориентир — **2–3 недели** плотной работы одного разработчика (все пункты ниже обязательны, без «бэклога»).

## Проблемы и конкретные решения

### Блок A — «Не заводится у разработчика»

**A1. Данные на Windows лежат не там**  
Сейчас путь `/app/data` — для Docker. На Windows без контейнера база не создаётся.  
**Решение:** в `paths.py` для локального запуска использовать `backend/data/` (или `%APPDATA%/PulsarAI/`).

**A2. Старт базы может упасть на чистой установке**  
Код пытается очистить таблицу `model_cache` до того, как она создана.  
**Решение:** сначала создать таблицы, потом миграции; опасные DELETE — только если таблица есть.

**A3. Порты Docker**  
**Решение:** прописать 18080 / 15173 / 18081 (см. выше) + обновить CORS и README.

---

### Блок B — «Кнопка есть — не работает»

**B1. Переключение модели («бесплатная версия»)**  
Фронт шлёт `{ model: "..." }` в теле запроса, бэкенд ждёт параметр в URL.  
**Решение:** на бэкенде принять JSON body (одна правка в `settings.py`).

**B2. Счётчик чатов `/chats/count`**  
Маршрут объявлен ниже, чем `/chats/{id}/messages`, поэтому слово `count` воспринимается как id чата.  
**Решение:** поднять маршрут `/count` выше в файле `chats.py`.

**B3. Прокрутка старых сообщений**  
`rowid` уже добавлен в незакоммиченных правках — нужно **прогнать сценарий** после фикса A1 (БД).

**B4. Остановка генерации ответа**  
При «Стоп» внутренний Promise может не завершиться — повторная отправка глючит.  
**Решение:** в `useStreamChat` и `streamChat` явно завершать Promise при Abort.

### VOICE-01 — Фильтрация текста для TTS-спикера

**Приоритет:** средний (качество озвучки)  
**Этап:** 4 (интерфейс / голос)  
**Статус:** ✅ выполнено

**Проблема:**  
LLM часто присылает символы, которые браузерный спикер (Web Speech API) пытается «произнести»: эмодзи, управляющие символы, markdown-разметка (`#`, `` ` ``, `*`), URL, спецсимволы. В результате озвучка ломается или звучит как набор мусора.

**Требование:**  
Перед передачей текста в `SpeechSynthesisUtterance` оставлять только **орфографические символы** (буквы, цифры, пробелы, знаки препинания для чтения) и явно разрешённые **`+`** и **`-`**. Всё остальное — удалять или заменять на пробел.

**Примеры того, что убрать:**

- Эмодзи и pictograph (Unicode categories `So`, `Sk`, emoji ranges)
- Управляющие символы (`\u0000`–`\u001F`, `\u007F`, zero-width, bidi marks)
- Markdown / разметка: `#`, `` ` ``, `*`, `_`, `|`, `>`, `[`, `]`, `(`, `)` — если не несут смысла для произношения
- URL, `@`, `#` в начале строки, блоки кода

**Примеры того, что оставить:**

- Буквы (латиница, кириллица и др. алфавиты, используемые в ответах)
- Цифры, пробелы, переносы строк (нормализовать в пробел)
- Знаки препинания: `. , ! ? ; : « » " ' …`
- Символы **`+`** и **`-`** (в т.ч. в числах и простых выражениях)

**Где внедрять:**

- `frontend/src/composables/useVoice.ts` — функция `useTTS().speak()` (единая точка перед `new SpeechSynthesisUtterance(text)`)
- Опционально: вынести в `frontend/src/utils/ttsSanitize.ts` с unit-тестами

**Критерии готовности:**

1. Нажатие «Озвучить» на ответе с эмодзи и markdown не озвучивает эмодзи и `#`/`` ` ``.
2. Обычный текст, числа и `+`/`-` читаются без искажений.
3. Пустой результат после фильтрации → не вызывать `speak`, показать нейтральный toast («Нечего озвучить»).

**Реализация:**

- `frontend/src/utils/ttsSanitize.ts` — фильтр (буквы, цифры, пробелы, `. , ! ? ; : « » " ' …`, `+`, `-`)
- `frontend/src/composables/useVoice.ts` — `speak()` применяет sanitize, возвращает `false` если нечего читать
- `frontend/src/components/chat/ChatMessages.vue` — toast «Нечего озвучить»
- Тесты: `frontend/src/tests/unit/ttsSanitize.test.ts`

### LOCAL-01 — Прогрессбар и синхронизация скачивания локальных моделей

**Проблема:**

- Нет прогрессбара — только текст «Скачивание...» на кнопке.
- **Server mode / несколько вкладок / несколько устройств:** на одном экране «Скачивание...», на другом — активная кнопка «Скачать», хотя загрузка уже идёт на backend.
- Риск параллельных запросов на одну модель и путаницы у пользователя.

**Требование:**  
1. **Прогрессбар** (процент / MB) на карточке модели до завершения или ошибки.  
2. **Единое состояние на backend** — все клиенты видят одно и то же: `idle` | `downloading` | `completed` | `failed` для каждой `model_id`.  
3. В server mode (и при нескольких вкладках SPA на одном ПК) кнопка «Скачать» **заблокирована везде**, пока идёт загрузка этой модели.

**Архитектура (server mode):**

| Слой | Решение |
|------|---------|
| Backend | In-memory или SQLite-таблица `model_download_jobs` (model_id, status, bytes_done, bytes_total, error, started_at) |
| API | `POST .../download/{id}` — старт (409 если уже `downloading`); `GET .../download/{id}/status` — polling; опционально SSE |
| Frontend | При открытии вкладки Local Models — poll статусов активных загрузок; интервал пока есть `downloading` |
| Standalone | То же API — один backend = один источник правды |

**Что сделать:**

1. **Backend:** хранить статус загрузки на сервере, не только в Vue `ref`.
2. **Backend:** отклонять повторный `POST download`, если модель уже в статусе `downloading` (HTTP 409 + текущий progress).
3. **Backend:** `progress_callback` в `model_downloader.py` → обновление `bytes_done` / `bytes_total`.
4. **Frontend:** `LocalModels.vue` — прогрессбар + poll/SSE; кнопка disabled если `status === 'downloading'` (с любого клиента).
5. **Frontend:** при `onMounted` и при возврате на вкладку — sync с `GET /admin/local-llm/downloads` (активные jobs).
6. i18n: «Скачивание… {percent}%», «{done} / {total} MB», «Загрузка уже идёт на сервере».

**Критерии готовности:**

1. TinyLlama (~600 MB): полоска 0→100% на устройстве, где нажали «Скачать».
2. **Вторая вкладка / второе устройство** на тот же backend: та же модель — «Скачивание… X%», кнопка disabled.
3. После завершения — на **всех** клиентах badge «Скачана» без ручного refresh.
4. При ошибке — `failed` и текст ошибки на всех клиентах; повторное скачивание доступно.
5. Повторный POST во время активной загрузки → 409, без второго параллельного скачивания.

**Файлы:**

- `backend/app/routes/admin.py` (+ job store, status endpoints)
- `frontend/src/components/LocalModels.vue`
- `frontend/src/api/settings.ts`

### CTX-01 — Кастомное контекстное меню (ПКМ)

**Приоритет:** средний (UX, привычное поведение десктопа)  
**Этап:** 4 (интерфейс)  
**Статус:** ✅ выполнено

**Реализация:**

- `frontend/src/utils/contextMenuActions.ts` — логика доступности пунктов
- `frontend/src/composables/useContextMenu.ts` — состояние и команды
- `frontend/src/components/common/ContextMenu.vue` — UI (Teleport, theme vars)
- Подключено: `ChatInput`, `MessageBubble`, `SettingsView`, `TheRightPanel`
- i18n: `context_menu.copy/cut/paste`
- Тесты: `frontend/src/tests/unit/contextMenuActions.test.ts`

**Проблема:**  
Сейчас при правом клике показывается **стандартное меню браузера** (или оно блокируется глобально). В SPA-чате это выглядит чужеродно и не даёт предсказуемых команд в зонах приложения. Нужно **своё контекстное меню** в стиле приложения с базовыми командами редактирования, как в ОС.

**Требование:**  
Реализовать кастомное контекстное меню по **ПКМ** с командами:

| Команда | Поле ввода чата | Сообщения в ленте чата | Прочие редактируемые поля (Settings, API key и т.д.) |
|---------|-----------------|------------------------|-----------------------------------------------------|
| **Копировать** | ✅ (если есть выделение) | ✅ (если есть выделение) | ✅ |
| **Вставить** | ✅ | ❌ | ✅ |
| **Вырезать** | ✅ (если есть выделение) | ❌ | ✅ |

**Ограничения (важно):**

- **Лента сообщений** (`MessageBubble`, код, markdown) — **только чтение**: доступно **Копировать** по выделенному тексту; **Вставить** и **Вырезать** **отсутствуют или disabled** (нельзя редактировать историю чата через буфер обмена).
- **Поле ввода** (`ChatInput.vue`, `textarea`) — полный набор **Копировать / Вставить / Вырезать** с учётом выделения и фокуса.
- Пункты меню **disabled**, когда команда недоступна: нет выделения → Cut/Copy; пустой clipboard / нет фокуса в input → Paste (где применимо).
- Не ломать **Ctrl+C / Ctrl+V / Ctrl+X** и выделение мышью — контекстное меню **дублирует**, а не заменяет горячие клавиши.

**Поведение:**

1. `@contextmenu.prevent` на целевых зонах → показать меню в координатах курсора (с clamp к viewport).
2. Закрытие: клик вне, Esc, scroll, смена чата.
3. Для **input/textarea** — `document.execCommand` или **Clipboard API** (`navigator.clipboard.readText` / `writeText`) с fallback; сохранять/восстанавливать selection при Paste/Cut.
4. Для **сообщений** — Copy через `window.getSelection()` → clipboard; без модификации DOM сообщения.
5. На «пустых» зонах UI (фон, сайдбар без текста) — либо не показывать меню, либо только Paste в input **не** предлагать (меню не открывается или одна disabled-группа — по решению при реализации; минимум — не показывать меню без текстового контекста).

**i18n:**  
«Копировать», «Вставить», «Вырезать» — ключи в `en.json` / `ru.json` (не hardcoded).

**Критерии готовности:**

1. ПКМ по выделенному тексту в **ответе ассистента** → «Копировать» работает; «Вставить» и «Вырезать» нет или disabled.
2. ПКМ в **поле ввода** с выделением → Copy и Cut; с фокусом и текстом в буфере → Paste.
3. Меню не обрезается краями окна; стиль согласован с темой (`var(--bg-panel)`, `var(--t1)`).
4. Нативное меню браузера **не всплывает** там, где включено кастомное.
5. Горячие клавиши Ctrl+C/V/X в input и при выделении в сообщении работают как до изменений.

**Файлы (ориентир):**

- `frontend/src/components/common/ContextMenu.vue` (или аналог) — UI меню

### I18N-01 — Backend-i18n: tier, reason, can_run_reason

**Приоритет:** средний (согласованность с UI-i18n)  
**Этап:** 4 (интерфейс) или отдельный проход после frontend i18n  
**Статус:** ✅ выполнено

**Реализация:**

- Backend: `reason_code` / `reason_params` в `system_check.py`, `can_run_model()` в `local_models.py`
- API: `/admin/system-check`, `/admin/local-llm/models`, `/admin/local-llm/settings`
- Frontend: `parseErrorCode(code, params)`, ключи в `errors.*`, `LocalModels.vue`, `SettingsView.vue`

**Проблема:**  
Frontend i18n (этап 4, п. 17) переводит подписи UI, но **тексты с backend** для локальных моделей и system check приходят **на английском** (или смешанно). Пользователь с русским интерфейсом видит английские `tier.reason`, `can_run_reason` и похожие строки в `LocalModels.vue` и настройках Local LLM.

**Примеры сейчас (backend):**

- `system_check.py` — `"System meets medium tier requirements"`, `"Insufficient resources: RAM …"`
- `local_models.py` / `can_run_model()` — `"Insufficient RAM: …"`, `"Insufficient CPU cores: …"`, `"Insufficient GPU VRAM: …"`

**Требование:**  
Единый подход как у ошибок провайдеров: backend отдаёт **`message_code` + параметры**, frontend переводит через `parseErrorCode()` / ключи `errors.*` в `en.json` / `ru.json`.

**Что сделать:**

1. **Backend:** в ответах `/admin/system-check`, `/admin/local-llm/models`, `/admin/local-llm/settings` добавить `message_code` (и опционально `message_params`) вместо или рядом с human-readable `reason` / `can_run_reason`.
2. **Backend:** коды для tier: `system_check_tier_medium`, `system_check_tier_light`, `system_check_tier_very_light`, `system_check_tier_unsupported` (+ params: `ram`, `cpu_cores`, `min_ram`, `min_cpu`).
3. **Backend:** коды для can_run: `local_model_insufficient_ram`, `local_model_insufficient_cpu`, `local_model_insufficient_vram`, `local_model_not_found` (+ params).
4. **Frontend:** в `LocalModels.vue`, `SettingsView` (local LLM status) — показывать `parseErrorCode(message_code, params)`; fallback на `reason`, если кода нет (обратная совместимость).
5. **Locales:** ключи в `errors.*` (ru/en), согласовать с уже существующими `system_check_*` где пересекается.

**Критерии готовности:**

1. RU-интерфейс + system check → tier message **на русском**.
2. Модель не тянется по RAM → `can_run_reason` **на русском** с подставленными GB/ядрами.
3. EN-интерфейс — те же коды, перевод на английский.
4. Старые клиенты без `message_code` не ломаются (fallback на `reason`).

**Файлы:**

- `backend/app/system_check.py`
- `backend/app/configs/local_models.py`
- `backend/app/routes/admin.py`
- `frontend/src/composables/useI18n.ts` (расширить `parseErrorCode` для params)
