# Оценка реализуемости этапов

Анализ текущей структуры проекта и технической реализуемости каждого этапа плана.

## Текущая структура проекта

**Бэкенд:**
- База данных: SQLite (aiosqlite)
- Таблицы: `chats`, `messages`
- Провайдеры: `BaseLLMProvider` (абстрактный), `VseLLMProvider`, `OpenRouterProvider`, `MockProvider`
- Схемы: Pydantic модели (`ChatRequest`, `ChatMessage`, `SettingsPayload`)
- Настройки: YAML хранилище (`storage.py`)
- Routes: `/settings` (конфигурация), `/chat` (чат), `/chats` (управление чатами)

**Фронтенд:**
- Vue.js + Pinia (stores)
- `chat.ts` - состояние чата
- `settings.ts` - состояние настроек

---

## Этап 1: Архитектурный фундамент (capabilities + list models)

**Реализуемость:** ✅ **Легко**

**Что нужно:**
1. Добавить `get_capabilities()` в `BaseLLMProvider`
2. Создать `ProviderCapabilities` схему в `schemas.py`
3. Добавить `list_models()` в `BaseLLMProvider`
4. Создать endpoint `/settings/capabilities`
5. Создать endpoint `/settings/models`

**Текущая база:**
- `BaseLLMProvider` уже существует и легко расширяем
- `VseLLMProvider` уже использует `models.list()` в `health_check()`
- Pydantic схемы уже используются

**Сложности:** Нет

---

## Этап 2: Добавление Anthropic

**Реализуемость:** ✅ **Легко**

**Что нужно:**
1. Создать `backend/app/providers/anthropic.py`
2. Реализовать `AnthropicProvider` с нативным API
3. Добавить `anthropic` в `requirements.txt`
4. Добавить в `init_provider()` в `settings.py`
5. Протестировать с Claude через VseLLM

**Текущая база:**
- Шаблон `VseLLMProvider` можно использовать как основу
- `init_provider()` уже имеет структуру для добавления новых провайдеров
- `SettingsPayload` уже включает `gigachat` в типах

**Сложности:** Нет

---

## Этап 3: Система лимитов и баланса

**Реализуемость:** ✅ **Легко**

**Что нужно:**
1. Создать таблицы `provider_balances` и `model_pricing` в SQLite
2. Реализовать endpoint `/settings/balance`
3. Реализовать endpoint `/settings/usage`
4. Создать сервис расчета лимитов
5. Добавить фоновую задачу для обновления балансов
6. Добавить предупреждения в UI

**Текущая база:**
- SQLite уже используется, есть пример миграции в `database.py`
- `database.py` имеет функции для работы с БД
- Routes уже существуют

**Сложности:**
- ⚠️ Фронтенд: нужно добавить UI для отображения баланса и предупреждений

---

## Этап 4: Бесплатные и платные модели

**Реализуемость:** ✅ **Легко**

**Что нужно:**
1. Расширить `model_pricing` с флагами (`is_free`, `daily_limit`, `model_group_id`)
2. Создать таблицу `model_groups`
3. Добавить бесплатные модели в реестр
4. UX для переключения при исчерпании баланса
5. Добавить индикаторы в UI

**Текущая база:**
- SQLite легко расширяем
- Реестр моделей можно хранить в БД или в коде

**Сложности:**
- ⚠️ Фронтенд: нужно добавить блок в чате с переключателем моделей
- ⚠️ Фронтенд: нужно добавить индикаторы "Бесплатно", "Лимит: X запросов/день"

---

## Этап 5: Миграции данных

**Реализуемость:** ✅ **Легко**

**Что нужно:**
1. Создать таблицу `schema_version`
2. Создать папку `backend/app/migrations/` с SQL файлами
3. Реализовать `upgrade_schema(from_version, to_version)`
4. Миграция настроек из YAML в БД
5. Автоматический запуск миграций при старте
6. Тестирование миграций

**Текущая база:**
- В `database.py` уже есть пример миграции (добавление `sort_order`)
- SQLite поддерживает ALTER TABLE

**Сложности:** Нет

---

## Этап 6: Локальная микро-LLM (опционально)

**Реализуемость:** ⚠️ **Средняя сложность**

**Что нужно:**
1. Система проверки системных требований (RAM, VRAM, CPU, диск)
2. Выбор модели на основе железа
3. Интеграция легкой модели (Phi-3, Qwen-1.5B)
4. Обучение/файнтюнинг на специфических данных
5. Fallback механизм
6. Режим "оффлайн-только"

**Текущая база:**
- Нет текущей базы для локальных моделей

**Сложности:**
- ⚠️ Проверка железа: нужно реализовать для разных ОС
- ⚠️ Обучение/файнтюнинг: требует отдельного процесса
- ⚠️ Производительность: зависит от железа пользователя

## Рекомендации

1. **Этапы 1-5 полностью реализуемы** с текущей архитектурой
2. **Основная сложность - фронтенд:**
